# Requirements

3. 동시 요청 처리

다수의 투표 요청이 거의 동시에 들어오는 상황에서도 다음 조건을 만족해야 합니다.

• 정상적인 투표가 유실되지 않아야 합니다..
• 동일 voterId의 중복 투표가 허용되지 않아야 합니다..
• 최종 집계 결과가 실제 성공한 투표 수와 일치해야 합니다..
구현 방식은 자유입니다.

Public URL을 만드는 방식에는 제한이 없습니다.
클라우드 배포, 터널링 서비스, 개인 서버 등 본인이 적절하다고 판단한 방법을 자유롭게 사용할 수 있습니다.
예:

https://your-service.example.com/health
https://your-service.example.com/api/result

## Feature Summary

- 사용자는 `jajang` 또는 `jjamppong` 중 하나를 선택해 투표할 수 있어야 한다.
- 사용자는 현재까지 저장된 짜장면/짬뽕 투표 수와 전체 투표 수를 조회할 수 있어야 한다.
- 외부 호출자는 서비스 정상 여부를 확인할 수 있는 health check API를 호출할 수 있어야 한다.
- 시스템은 동일한 `voterId`의 중복 투표를 막아야 한다.
- 이 서비스에서 `voterId`는 곧 `userId`이며, 사용자 식별자 기준으로 중복 투표를 막아야 한다.
- 시스템은 동시에 들어오는 투표 요청에서도 성공한 투표를 유실하지 않고 정확히 집계해야 한다.
- 서비스는 Docker로 실행할 수 있어야 하며, 8080 포트로 API를 제공해야 한다.
- 서비스는 Public URL을 통해 외부 인터넷 환경에서 호출 가능해야 한다.
- 애플리케이션 또는 Docker Container 재시작 이후에도 기존 투표 데이터가 유지되어야 한다.

## Domain Rules

명시된 도메인 규칙:

- 투표 등록 API는 `POST /api/vote`이다.
- 투표 요청 body는 `choice`와 `voterId`를 포함한다.
- `choice`는 `jajang`, `jjamppong`만 허용한다.
- 동일한 `voterId`는 한 번만 투표할 수 있다.
- `voterId`는 이 서비스의 `userId`와 같은 값으로 취급한다.
- 이미 투표한 `voterId`로 다시 투표하면 `409 Conflict` 등 적절한 오류를 반환한다.
- 잘못된 `choice`, 누락된 값 등 비정상 요청은 적절한 오류로 처리한다.
- 결과 조회 API는 `GET /api/result`이다.
- 결과 조회 응답은 `jajang`, `jjamppong`, `total` 투표 수를 포함한다.
- 결과 조회 값은 실제 저장된 투표 결과와 일치해야 한다.
- Health check API는 `GET /health`로 제공한다.
- Health check 정상 상태는 HTTP 200으로 응답한다.
- 다수의 동시 투표 요청에서도 정상 투표가 유실되지 않아야 한다.
- 다수의 동시 투표 요청에서도 동일 `voterId`의 중복 투표가 허용되지 않아야 한다.
- 최종 집계 결과는 실제 성공한 투표 수와 일치해야 한다.
- 서비스는 Docker를 통해 실행할 수 있어야 한다.
- 서비스는 8080 포트를 사용해야 한다.
- Session 1 종료 시 Public URL을 제출해야 하며, `localhost`나 사설 IP는 인정되지 않는다.
- 애플리케이션 또는 Docker Container 재시작 후에도 서비스가 정상적으로 다시 시작되어야 한다.
- 재시작 후에도 기존에 정상 처리된 투표 데이터가 유지되어야 한다.
- 재시작 후 동일한 `voterId`가 다시 투표해도 기존 기록 기준으로 중복 투표가 처리되어야 한다.

추론한 도메인 규칙:

- `voterId`는 투표자를 식별하는 외부 입력값이며, 이 서비스에서는 `userId`와 같은 의미로 사용한다.
- 같은 `voterId`/`userId` 문자열은 같은 사용자로 본다.
- 투표 결과의 `total`은 `jajang + jjamppong` 값과 같아야 한다.
- 중복 투표 방지는 애플리케이션 메모리만이 아니라 영속 저장소 기준으로 보장되어야 한다.
- 동시 중복 투표는 하나의 요청만 성공하고 나머지는 충돌 오류로 처리되어야 한다.
- 투표 집계는 별도 캐시보다 저장된 투표 데이터를 기준으로 산출하는 것이 기본이다.
- Public URL은 구현 코드에 하드코딩하지 않고 실행 환경 또는 터널링 도구로 구성한다.

## Assumptions

- 인증/인가 요구사항은 없다.
- 투표 성공 응답 형식과 상태 코드는 API 계약 문서화 단계에서 확정한다.
- 오류 응답 형식은 기존 프로젝트의 공통 오류 응답 규칙을 우선 따른다.
- `choice` 값은 대소문자를 구분하며, 요구사항에 적힌 소문자 값만 허용한다.
- `voterId`는 필수 값이며 blank 문자열은 유효하지 않은 요청으로 처리한다.
- 데이터 저장 방식은 구현 단계에서 선택하되, 재시작 후 데이터 유지와 동시성 정합성을 만족해야 한다.
- 중복 투표 방지는 저장소의 unique constraint 또는 그에 준하는 원자적 보장을 우선 사용한다.
- Docker 단독 실행 시 데이터 유지 방식은 볼륨 또는 외부 영속 저장소 연결로 보장한다.
- Public URL은 로컬 개발 환경에서는 ngrok 같은 터널링 서비스 사용을 기본값으로 둔다.

## Open Questions

- `POST /api/vote` 성공 응답은 `200 OK`와 `201 Created` 중 어떤 상태 코드를 사용할 것인가?
- 투표 성공 응답 body에 저장된 투표 정보를 반환할 것인가, 공통 성공 응답만 반환할 것인가?
- `voterId`의 최대 길이, 허용 문자, 앞뒤 공백 trim 여부를 어떻게 정할 것인가?
- Docker 실행 예시를 단일 컨테이너 중심으로 제공할 것인가, DB 포함 compose 중심으로 제공할 것인가?
- Public URL은 README에 예시만 남길 것인가, 실제 세션 종료 시점 URL을 별도로 제출할 것인가?

## Out Of Scope

- 로그인, 회원가입, 인증, 인가.
- 투표 수정 및 삭제.
- 관리자용 투표 관리 API.
- 후보 추가, 다중 설문, 설문 종료 시간.
- 실시간 결과 스트리밍, WebSocket, Server-Sent Events.
- 운영용 클라우드 배포 자동화.
- 고급 통계, IP 제한, rate limit, 부정 투표 탐지.
